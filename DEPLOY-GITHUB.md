# Deploying Provenance to GitHub Pages

This folder is a plain, dependency-free static site — 21 HTML pages, no
build step. Two ways to get it live.

## Option A — deploy from a branch (simplest, no Actions needed)

1. Create a new GitHub repo (or use an existing one).
   - If you want the site at the bare `https://<username>.github.io`, the
     repo must be named exactly `<username>.github.io`.
   - Any other repo name serves the site at
     `https://<username>.github.io/<reponame>/` instead — that's fine too;
     every link on this site is a relative filename (`href="about.html"`,
     not `href="/about.html"`), so it works correctly at either a root
     domain or a subpath with zero changes.
2. Push the contents of this folder to the repo's default branch (commit
   the `.nojekyll` file too — it's a real, intentional file, not
   incidental).
3. In the repo, go to **Settings → Pages**, and under "Build and
   deployment" choose **Deploy from a branch**, pick your default branch
   and the `/ (root)` folder, then save.
4. GitHub gives you a live URL within a minute or two.

## Option B — GitHub Actions (if you'd rather deploy via CI)

A ready-to-use workflow is already included at
`.github/workflows/pages.yml`. To use it instead of Option A:

1. Push this folder (including `.github/workflows/pages.yml`) to your repo.
2. In **Settings → Pages**, under "Build and deployment", choose
   **GitHub Actions** as the source instead of "Deploy from a branch".
3. Push to `main` (or run the workflow manually from the Actions tab) —
   it uploads this folder as-is and deploys it. No build command needed
   since there's nothing to compile.

## Before you treat this as production-ready

- **`robots.txt` and `sitemap.xml` contain a placeholder URL**
  (`https://REPLACE-WITH-YOUR-GITHUB-PAGES-URL`) because the real URL
  depends on the repo name / custom domain you choose in Option A step 1.
  Once you know it, find-and-replace that placeholder in both files.
- If you attach a custom domain (**Settings → Pages → Custom domain**),
  add a `CNAME` file at the root containing just that domain — GitHub
  writes this for you automatically the first time you set a custom
  domain through the Pages settings UI, so you usually don't need to
  create it by hand.
- Every `[BRACKETED PLACEHOLDER]` on the site itself (inquiry email,
  consultation phone number, several photo placeholders, the Journal's
  opening-date entry, a few procedure-specific specifics) is a stand-in
  for a real fact or asset that still needs to be supplied.
- Photos are dashed placeholder boxes throughout — there are no real
  images in this export yet.
- There's no contact-form backend. GitHub Pages can't run server-side
  code at all (unlike Netlify Forms) — a real contact form here would
  need a third-party form service (e.g. Formspree) or a separate backend.
- No analytics, cookie consent, or chat widget is wired in — intentional
  for now; the Privacy Notice page currently states the site "does not
  use cookies, analytics, or third-party tracking scripts," so keep that
  copy in sync with whatever gets added later.

## Keeping this in sync with the design canvas

This export was generated by `export_github_pages.py` (in the parent
folder), which reuses the exact same page-rendering code as
`export_netlify.py` — the two exports are always in sync with each other.
If the canvas gets edited again later, re-run
`python3 export_github_pages.py` to regenerate this folder from the latest
content before redeploying.
